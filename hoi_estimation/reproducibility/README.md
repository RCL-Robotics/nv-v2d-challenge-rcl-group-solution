### Running from another location
- **No built-in paths.** Every script, including the GT-only ones in `../diagnostics/`, takes its locations from
  environment variables or arguments and stops if a required one is unset; code locations are resolved relative to
  the checkout.

  | variable | meaning | needed by |
  |---|---|---|
  | `V2D_ROOT` (required) | the data root | every step |
  | `APPTAINER` | apptainer binary (default `apptainer` on `PATH`) | shell wrappers |
  | `V2D_RUN` | local scratch root of the per-episode CARI4D runs | `run_local.sh`, `exp_*.sh`, `diagnose_episode.py` |
  | `HOST_PY` | host python for the three host-python steps (default `python3`) | `check_steps.sh`, runbooks |
  | `V2D_SUPPORT_OUT` | support intermediates (default `$V2D_ROOT/support`) | `support/` |
  | `V2D_VDA`, `V2D_DEPTHPRO_CKPT` | Video-Depth-Anything checkout, DepthPro checkpoint | `vda_depth.py`, `estimate_focal.py` (exploratory, not in the chain) |
  | `CLAUDE_BIN`, `CODEX_BIN`, `T2_PY` | agent CLIs (default: found on `PATH`), python for `extract_t2_human.py` | `agent/run_*.sh`, `tier2_refine/run_all.sh` |

  Bind the root into the images (`-B $V2D_ROOT`). For image calls with `--cleanenv`/`--containall`, also export
  `APPTAINERENV_V2D_ROOT=$V2D_ROOT`. The runbooks write the workstation paths as `$N` (= `$V2D_ROOT`), `$REPO`
  (= `<checkout>/hoi_estimation`), `$A` and `$V2D_RUN`. The files under `release_files/` and `../agent_records/`
  are verbatim copies of released or agent-written files and keep the paths they were written with.
- **Absolute paths inside data files:** the `bundle` fields of the `logs/*.json` files and the `mesh` field of
  `support/ep*/support.json` hold NAS paths. They are informational only: the scripts locate bundles by variant name
  (`eval_official.bundle_path`) and the support meshes by class (`support/contact.py`, `package.py`). The six
  `experiments/M1/episode_*/coconet.pth` are absolute symlinks to the NAS (also in the server copy, where they are
  therefore broken). In a copy, recreate them with
  `cd $V2D_ROOT/experiments/M1 && for e in 3 6 12 14 16 21; do d=$(printf episode_%06d $e); ln -sfn ../../M1_prompt_v2/out/$d/inference/coconet.pth $d/coconet.pth; done`.
- **GPU:** the images are built for sm_80–sm_90 (`TORCH_CUDA_ARCH_LIST="8.0 8.6 8.9 9.0"` for nvdiffrast, pytorch3d,
  kaolin, FoundationPose; torch 2.5.1+cu124). The original runs used RTX 6000 Ada (sm_89). The image does **not** run
  its GPU code on Blackwell (sm_120) GPUs such as the RTX PRO 6000 of the training server; use an Ampere, Ada or
  Hopper GPU.
- **Host python:** three CPU steps ran on the host, not in the image: `postproc_depth_blend.py`,
  `build_release_opus.py` and `build_release_combined.py`. They reproduce bit-identically with python 3.12.13,
  numpy 2.5.2, scipy 1.17.0, torch 2.10.0, trimesh 4.11.1 (`environment/pip_freeze_host_venv.txt`). Run in the image
  (numpy 1.26.3, torch 2.5.1), `postproc_depth_blend.py` gives float-level different bundles.

## 5. Known issue in two releases: `frame_references/`
`build_release_opus.py` copies `frame_references/` unchanged from `tier3_s1_20261020`, and `build_release_combined.py`
copies it unchanged from the opus release. In `tier3_opus_20261021` and `tier3_frame0_supports_20261024` these files
therefore hold the **s1** object trajectories, not the trajectories in `reconstructed_data/` (mean translation
difference over the 30 episodes 6.8 cm and 9.6 cm, up to 0.60 m for one episode). `tier3_s1_20261020` is consistent.
The scripts are left as they ran, so that they rebuild the released files exactly. Anyone packing a submission with
`--frame-references` from these two releases should regenerate the files from `reconstructed_data/*/object_pose_xyz_wxyz.npy`
(the loop in `s1_runbook.md` 10).

**Why the contact numbers change:** `contact.py` samples 400 points on the object mesh with `obj.sample(400)` after
`np.random.seed(0)`. With the image's trimesh 5.1.1 this sampling no longer uses numpy's global generator, so every
run draws different points (two runs on the same input: ep2 gap −0.050 vs +0.060 cm). The released values come from
one such draw and cannot be regenerated exactly. In this re-run the median rest gaps differ from the release by
≤ 0.26 cm, `contact_shift_m` by ≤ 0.4 mm (ep2) and the GT-free snapped trajectories
(`support/ep*/object_poses_world_snapped.npz`, not part of any release) by ≤ 1.05 cm (ep11). For ep11, the
leaning distance and the number of rest frames with support below change from run to run. These fields are
diagnostics: the released object trajectory (`object_poses_world.npz`) is the unsnapped one and is unaffected. With
the host trimesh 4.11.1 the sampling is deterministic, but it gives a third set of points. The code is left as it was
when the release was made.

It has not yet been checked against `environment/data_manifest.sha256.gz` on the server; the two images were
(sha256 as in section 4).

Summary: every CPU step except the contact sampling is byte-identical (and the three re-run on the server are too). The GPU
steps that optimise the object or the support (solve.py, support fit) are bit-identical on the same GPU model; the GPU
SOMA/MHR decoding of the human gives float-level differences, which reach the object only at the 1e-6 level (FF2,
JC2s1) and leave the released object poses unchanged (build_release).


**Stages:** `setup baseline e2 p1 m1 ffw pnp ff2 jc2s1 db release export agents opus frame0 support combined`.

**What it does with the inputs.**
- It reads the dataset, weights and images only, and binds them read-only into the images.
- It writes only under `V2D_ROOT` and `V2D_RUN`.
- `setup` stops if any input file is unreadable or a Git LFS file is still a pointer.

**Episode routing, as in the submission (`s1_runbook.md`).**
- E2/P1 path: the 20 episodes listed in section 2.
- M1 path: episodes 3, 6, 12, 14, 16 and 21.
- Baseline path: all other episodes.
- Support surfaces: the 14 placement episodes in `support/common.py`.
- Agent runs keep the submission's run names, `CL2*_ep<eee>`.

**Cost of a full run** (all 30 episodes, one GPU), from `AGENTIC_WORKFLOW.md` (resource usage):
- the CARI4D baseline: about 28 GPU-h;
- E2, M1 and the first-frame steps: an estimated 10–20 GPU-h (not logged per step);
- the agents: 30 runs × at most 90 min; `AGENT_P` sets how many run at once.
